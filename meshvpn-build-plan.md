# MeshVPN — Claude Code Build Plan

## Project summary

A self-hosted, containerised mesh VPN platform running across three nodes:
- **Node A**: Proxmox gateway VM (Debian 12, Docker Compose, full mesh daemon + leader)
- **Node B/C**: Raspberry Pi (Raspberry Pi OS or HA OS add-on, Docker Compose, follower nodes)

Clients (phones, laptops, PCs) connect via OpenVPN over TCP 443. The mesh uses WireGuard
internally between nodes. Cloudflare DNS + multi-remote .ovpn files handle failover.
A web frontend on every node lets you manage clients, servers, and routing settings.

---

## Decisions made (Claude's choices)

| Concern | Choice | Reason |
|---|---|---|
| Backend language | Python 3.12 (FastAPI) | One language, async, runs on ARM + x86 |
| Mesh state sync | SQLite + custom replication over HTTPS | No external coordinator, simple, reliable |
| Leader election | Bully algorithm (highest priority wins) | Simple to implement correctly, no Raft complexity |
| Config format | `mesh.yaml` (single file per node) | Human-readable, easy to version |
| Frontend | React + Vite (served by Nginx) | Fast build, small image |
| WireGuard config | Generated via Python templates, applied via `wg syncconf` | Zero-downtime peer updates |
| OpenVPN config | Generated via Python + inline PKI (cryptography lib) | No EasyRSA dependency |
| PKI | Python `cryptography` library, CA on leader, replicated | No shell dependency |
| Cloudflare failover | CF API (A record per node) + TTL 60s + multi-remote in .ovpn | Both layers as agreed |
| Health check | HTTP probe + ICMP ping + WG handshake age | Three independent signals |
| Raspberry Pi nodes | Raspberry Pi OS + Docker (or HA add-on as stretch goal) | Full Docker support |
| Subnet enforcement | OpenVPN `push route` + iptables DROP for anything else | Server-side, not client-trust |
| Auth | Username + bcrypt password, JWT session tokens | Simple, no OAuth dependency |

## Phase 1 — Project scaffold and config system

### Goal
Running containers on Node A. `docker compose up` starts all services. Config is read from
`mesh.yaml`. Nothing works yet but all services start without errors.

### Tasks

**1.1 — mesh.yaml schema**
Create `mesh.yaml.example` with all fields. Create `core/config.py` that:
- Loads and validates `mesh.yaml` using Pydantic
- Exposes a global `settings` object imported by all other modules
- Validates required fields: `node.name`, `node.public_ip`, `node.wg_port`, `node.vpn_port`
- For join mode: validates `mesh.join_addr` and `mesh.join_token` are present
- Exits with a clear error message if config is invalid

```yaml
# mesh.yaml — full schema
node:
  name: "node-a"
  public_ip: "1.2.3.4"          # or hostname
  wg_port: 51820
  vpn_port: 443
  api_port: 8080
  ui_port: 3000
  priority: 100                  # higher = preferred leader

mesh:
  mode: "leader"                 # "leader" or "join"
  join_addr: ""                  # "1.2.3.4:8080" for join mode
  join_token: ""                 # from leader UI

network:
  client_subnet: "10.8.0.0/24"
  mesh_subnet: "10.99.0.0/24"
  allowed_lan: "192.168.100.0/24"

routing:
  mode: "weighted"               # weighted | random | fastest | failover
  weight: 100
  health_interval: 3
  failover_threshold: 3

cloudflare:
  enabled: true
  api_token: ""                  # or set CF_API_TOKEN env var
  zone_id: ""
  domain: "vpn.yourdomain.com"
  ttl: 60

auth:
  admin_password: ""             # or set ADMIN_PASSWORD env var — bcrypt on startup
```

**1.2 — docker-compose.yml**
Define all services with correct dependencies, volumes, and capabilities:
- `core`: FastAPI, port 8080, mounts `/data` volume and `/etc/meshvpn/mesh.yaml`
- `wg-manager`: host network mode, `NET_ADMIN` + `SYS_MODULE` capabilities
- `router`: host network mode, `NET_ADMIN` capability
- `openvpn`: host network mode, `NET_ADMIN`, reads config from `/data/openvpn/`
- `haproxy`: ports 443, reads config from `/data/haproxy/haproxy.cfg`
- `cloudflare`: no special caps, reads state from core API
- `frontend`: port 3000, Nginx static serve

Named volume: `meshvpn-data` → `/data` in all containers that need it.

**1.3 — SQLite schema** (`core/db.py`)
Tables:
```sql
nodes (id, name, public_ip, wg_pubkey, wg_ip, api_port, wg_port, vpn_port, 
       priority, status, last_seen, joined_at)

clients (id, name, wg_pubkey, wg_ip, ovpn_ip, created_at, cert_pem, key_pem)

mesh_config (key, value, updated_at)   -- replicated key/value store

routing_rules (id, mode, weights_json, updated_at)

health_log (node_id, timestamp, wg_ok, api_ok, ping_ok, latency_ms)
```

**1.4 — Dockerfiles**
All images: `python:3.12-slim` base. Install deps from `requirements.txt`. No root user in
production (except wg-manager and router which need NET_ADMIN).

## Phase 2 — Core daemon: leader mode

### Goal
Node A starts as leader. Generates its WireGuard keypair. Initialises DB. Starts API.
Generates a join token. Frontend shows the node is online.

### Tasks

**2.1 — Startup sequence** (`core/main.py`)
On boot, in order:
1. Load and validate `mesh.yaml`
2. Initialise SQLite DB (create tables if not exist)
3. If `mesh.mode == "leader"`:
   - Check if this node is already in DB (restart case) — if yes, skip keygen
   - Generate WireGuard keypair (`wg genkey` / `wg pubkey`) if not already stored in DB
   - Assign this node `wg_ip` = first address in `mesh_subnet` (e.g. `10.99.0.1`)
   - Insert self into `nodes` table with `status = "leader"`
   - Generate a join token (32-byte random hex, stored in `mesh_config`)
   - Write initial WireGuard config via template → signal wg-manager
   - Write initial OpenVPN server config via template → signal openvpn container
   - Write initial HAProxy config via template → signal haproxy
   - Start Raft heartbeat loop (background task)
   - Start health check loop (background task)
4. Start FastAPI application

**2.2 — PKI generation** (inside `core/main.py` startup, using `cryptography` lib)
- Generate CA key + self-signed cert (stored in `/data/pki/ca.key` + `ca.crt`)
- Generate server key + CSR + sign with CA (stored in `/data/pki/server.key` + `server.crt`)
- Generate Diffie-Hellman params (2048-bit, stored in `/data/pki/dh.pem`)
- Generate TLS auth key (`openvpn --genkey`) stored in `/data/pki/ta.key`
- On restart: if files exist, skip generation

**2.3 — WireGuard config template** (`core/templates/wg0.conf.j2`)
```ini
[Interface]
Address = {{ node.wg_ip }}/24
PrivateKey = {{ node.wg_privkey }}
ListenPort = {{ node.wg_port }}
PostUp = iptables -A FORWARD -i wg0 -j ACCEPT; iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
PostDown = iptables -D FORWARD -i wg0 -j ACCEPT; iptables -t nat -D POSTROUTING -o eth0 -j MASQUERADE

{% for peer in peers %}
[Peer]
PublicKey = {{ peer.wg_pubkey }}
AllowedIPs = {{ peer.wg_ip }}/32
Endpoint = {{ peer.public_ip }}:{{ peer.wg_port }}
PersistentKeepalive = 5
{% endfor %}
```

**2.4 — OpenVPN server config template** (`core/templates/server.ovpn.j2`)
```
port {{ node.vpn_port }}
proto tcp
dev tun
ca /data/pki/ca.crt
cert /data/pki/server.crt
key /data/pki/server.key
dh /data/pki/dh.pem
tls-auth /data/pki/ta.key 0
server {{ client_subnet_base }} {{ client_subnet_mask }}
push "route {{ allowed_lan_base }} {{ allowed_lan_mask }}"
push "route-nopull"
keepalive 10 30
cipher AES-256-GCM
user nobody
group nogroup
persist-key
persist-tun
status /data/openvpn/status.log
verb 3
```

**2.5 — HAProxy config template** (`haproxy/haproxy.cfg.j2`)
```
global
    log stdout format raw local0

defaults
    mode tcp
    timeout connect 5s
    timeout client 60s
    timeout server 60s
    log global

frontend vpn_in
    bind *:443
    default_backend openvpn_local

backend openvpn_local
    server ovpn 127.0.0.1:1194 check
```
HAProxy is kept simple in MVP — it's the TCP frontend for OpenVPN. Stunnel added later.

**2.6 — REST API endpoints** (`core/api/`)

Auth (`/api/auth`):
- `POST /api/auth/login` → `{username, password}` → JWT token (24h expiry)
- `POST /api/auth/logout`

Nodes (`/api/nodes`):
- `GET /api/nodes` → list all nodes with status
- `GET /api/nodes/self` → this node's info
- `POST /api/nodes/join` → called by new nodes (requires join token in header)
- `DELETE /api/nodes/{id}` → remove a node (leader only)
- `GET /api/nodes/join-token` → get/rotate join token (auth required)

Clients (`/api/clients`):
- `GET /api/clients` → list all VPN clients
- `POST /api/clients` → `{name}` → creates client, returns id
- `GET /api/clients/{id}/ovpn` → download .ovpn bundle
- `DELETE /api/clients/{id}` → revoke client

Routing (`/api/routing`):
- `GET /api/routing` → current mode + weights
- `PUT /api/routing` → update mode/weights → takes effect within one health cycle

Health (`/api/health`):
- `GET /api/health` → this node's health summary (used by peers to probe us)
- `GET /api/health/mesh` → all nodes' health (aggregated)

Sync (`/api/sync`) — internal, not authenticated by JWT but by shared mesh secret:
- `GET /api/sync/snapshot` → full DB export (leader only, followers call this on join)
- `POST /api/sync/delta` → push a change from leader to followers
- `POST /api/sync/heartbeat` → leader sends this to each follower every 2s

**2.7 — Client .ovpn bundle generation** (`core/api/clients.py`)
When a client is created:
1. Generate client key + CSR + sign with CA
2. Store cert + key in `clients` table
3. On download, render `client.ovpn.j2`:

```
client
dev tun
proto tcp
# All known nodes listed — client tries in order, falls back automatically
remote {{ nodes[0].public_ip }} 443
remote {{ nodes[1].public_ip }} 443
remote {{ nodes[2].public_ip }} 443
remote-random
resolv-retry infinite
nobind
persist-key
persist-tun
cipher AES-256-GCM
verb 3
<ca>{{ ca_cert }}</ca>
<cert>{{ client_cert }}</cert>
<key>{{ client_key }}</key>
<tls-auth>{{ ta_key }}</tls-auth>
key-direction 1
```

## Phase 3 — Join logic and follower mode

### Goal
Node B starts with `mode: join` in mesh.yaml. It calls Node A, authenticates with the join
token, receives the full config snapshot, sets itself up, and appears in Node A's frontend.
This must also work if Node A is temporarily unreachable at join time — node B retries
indefinitely until it can reach any known leader.

### Tasks

**3.1 — Join sequence** (`core/main.py`, join mode)
1. Load `mesh.yaml`, read `join_addr` and `join_token`
2. Generate own WireGuard keypair (stored locally)
3. Call `POST https://{join_addr}/api/nodes/join` with:
   - Header: `X-Join-Token: {token}`
   - Body: `{name, public_ip, wg_pubkey, wg_port, vpn_port, api_port, priority}`
4. Leader responds with:
   - This node's assigned `wg_ip` in the mesh subnet
   - Full `nodes` table snapshot
   - PKI: `ca.crt`, `ta.key`, `dh.pem` (no private keys)
   - Server cert/key for this node (signed by leader CA)
   - Current routing config
   - Mesh shared secret (for sync endpoint auth)
5. Write all received files to `/data/`
6. Generate WireGuard config (all peers) → signal wg-manager
7. Generate OpenVPN server config → signal openvpn
8. Start as FOLLOWER — subscribe to heartbeats from leader

**3.2 — Retry logic**
If join fails (leader unreachable): retry every 10 seconds, log each attempt.
If any *other* known node is reachable (from a previously cached peer list), try joining
via that node — it will proxy the request to the current leader or, if it is the leader,
handle it directly. Cached peer list stored in `/data/peers_cache.json` — written after
every successful sync.

**3.3 — Leader-side join handler** (`core/api/nodes.py`)
- Validate join token (constant-time compare)
- Assign next free IP in `mesh_subnet`
- Sign a server cert for the joining node using the CA
- Insert node into `nodes` table
- Broadcast delta to all existing followers: "new peer added"
- Each follower updates its WG config to add the new peer (via wg syncconf — no restart)

**3.4 — wg-manager apply logic** (`wg-manager/manager.py`)
- Polls core API `GET /api/nodes` every 3 seconds
- If peer list changed: regenerate `wg0.conf` and run `wg syncconf wg0 /data/wg/wg0.conf`
- Never restarts WireGuard — only syncs config
- Runs `wg show wg0 latest-handshakes` every 3s — posts results back to core health endpoint
- A peer whose last handshake is > 15s ago is marked `wg_degraded`
- A peer whose last handshake is > 30s ago is marked `wg_dead`

## Phase 4 — Health checks and failover

### Goal
Kill Node A. Node B detects it within 6 seconds, runs election, wins, becomes leader,
updates Cloudflare DNS to remove Node A's A record, and clients auto-reconnect to Node B.
Node A comes back — detects a new leader, joins as follower.

### Tasks

**4.1 — Health check loop** (`core/main.py`, background task)
Every `health_interval` seconds, for each peer:
1. `wg show wg0 latest-handshakes` — check handshake age (via wg-manager)
2. `GET https://{peer.api_addr}/api/health` with 2s timeout
3. ICMP ping (1 packet, 1s timeout) via `asyncio subprocess`

Score each peer: 0–3 healthy signals. Store in `health_log`. Expose via `/api/health/mesh`.

**4.2 — Election logic** (`core/election.py`)

Bully algorithm:
1. FOLLOWER misses `failover_threshold` consecutive heartbeats from leader → enters CANDIDATE
2. CANDIDATE sends `POST /api/nodes/election` to all peers with its own priority score
3. Any peer with higher priority responds `NACK` → that peer starts its own candidacy
4. If no higher-priority NACK within 3s → this node wins, sets itself LEADER
5. New LEADER:
   - Updates its own `nodes` row to `status = "leader"`
   - Broadcasts `POST /api/sync/new-leader` to all peers
   - Takes over heartbeat loop
   - Triggers Cloudflare DNS update (remove dead node, ensure self is present)
   - Regenerates HAProxy config if needed

**4.3 — Isolated mode** (`core/state.py`)
If ALL peers fail health check:
- Set state = ISOLATED
- Write `/data/state/isolated` flag file
- Router removes all mesh routes
- HAProxy continues serving local OpenVPN only
- Cloudflare updater removes this node's A record (clients won't be sent here)
- Node keeps trying to reach peers every 10s
- When a peer responds: clear isolated flag, re-enter CANDIDATE, run election

**4.4 — Router service** (`router/router.py`)
Polls core API every 3s for peer health + routing config:
- For each `wg_ok` peer: ensure `ip route` entry exists via `wg0`
- For each `wg_dead` peer: remove route
- Routing modes:
  - `weighted`: use `ip route` metric based on peer weight config
  - `random`: rotate `ip route` primary every N seconds
  - `fastest`: use lowest latency from health_log
  - `failover`: use highest-priority live peer only
- Never removes route to self (local traffic always works)

**4.5 — Cloudflare DNS updater** (`cloudflare/updater.py`)
Polls core API `/api/health/mesh` every 10s:
- For each node: if healthy → ensure A record exists for `{node.name}.vpn.yourdomain.com`
- If unhealthy → delete that node's A record
- Also manages the root `vpn.yourdomain.com` records (one per healthy node)
- Only the current LEADER runs the full Cloudflare update logic
- Followers update only their own record (to avoid race conditions)
- Uses `cloudflare` Python library (`pip install cloudflare`)
- All CF operations idempotent — safe to run repeatedly

## Phase 5 — Web frontend

### Goal
React SPA accessible at `:3000` on every node. Login with admin password. Four pages:
Dashboard, Clients, Servers, Routing. All data from the core API.

### Tasks

**5.1 — Auth flow**
Login page → POST to `/api/auth/login` → store JWT in memory (not localStorage — use
React context). All API calls include `Authorization: Bearer {token}`.

**5.2 — Dashboard page**
- Card per node: name, public IP, status badge (LEADER / FOLLOWER / CANDIDATE / ISOLATED / DEAD)
- Per node: WireGuard handshake age, ping latency, API reachable yes/no
- Auto-refreshes every 5 seconds via polling (no websockets in MVP)
- Shows current routing mode

**5.3 — Clients page**
- Table of all VPN clients: name, created date, assigned IP
- "Add client" button → modal → enter name → POST `/api/clients` → show download button
- Download button → GET `/api/clients/{id}/ovpn` → browser downloads the file
- Delete button → confirm modal → DELETE `/api/clients/{id}`
- Client .ovpn always includes all currently healthy nodes as `remote` lines

**5.4 — Servers page**
- List all joined nodes
- "Add server" button → shows join token + instructions:
  ```
  1. Copy mesh.yaml.example to your new server
  2. Set mode: join
  3. Set join_addr: {this_node_ip}:{api_port}
  4. Set join_token: {token}
  5. Run: docker compose up -d
  ```
- "Rotate token" button → invalidates old token, shows new one
- Remove node button (leader only) → removes from mesh, revokes its certs

**5.5 — Routing page**
- Current mode selector: Weighted / Random / Fastest / Failover-only
- Per-node weight sliders (only active in Weighted mode)
- Health interval input (seconds)
- Failover threshold input (missed heartbeats)
- Save button → PUT `/api/routing` → propagated to all nodes via sync

**5.6 — Nginx config** (`frontend/nginx.conf`)
- Serve static build from `/usr/share/nginx/html`
- Proxy `/api/` → `http://core:8080/api/` (so frontend and API are same-origin)
- Gzip enabled, cache headers for static assets

## Phase 6 — Raspberry Pi support

### Goal
Node B or C is a Raspberry Pi running Raspberry Pi OS. Same `docker compose up` command
works on ARM64/ARM32.

### Tasks

**6.1 — Multi-arch Docker images**
All Dockerfiles use `python:3.12-slim` (available for arm64 and armhf) and
`node:20-alpine` (multi-arch). No x86-specific deps. Test list:
- `cryptography` library: available on ARM via pip wheel ✓
- `wireguard-tools`: `apt install wireguard-tools` in Dockerfile ✓
- `openvpn`: official image is multi-arch ✓
- `haproxy:2.9`: multi-arch ✓

**6.2 — Raspberry Pi OS setup script** (`scripts/install-pi.sh`)
One script that:
1. `apt install -y docker.io docker-compose-plugin`
2. `modprobe wireguard` (check if kernel module available; Pi OS 5.x has it)
3. Enables IP forwarding in `/etc/sysctl.conf`
4. Creates `/etc/meshvpn/` directory
5. Prints instructions to fill in `mesh.yaml`

**6.3 — HA OS add-on (stretch goal, documented but not built in MVP)**
Document the path: HA OS uses Supervisor which runs Docker containers as add-ons.
An add-on is a Docker image + `config.yaml` descriptor. The mesh node image can be
packaged as an add-on with `host_network: true` and `full_access: true` capabilities.
This is post-MVP work — document the structure in `docs/ha-addon.md`.

## Phase 7 — Integration, hardening, and testing

### Tasks

**7.1 — End-to-end test script** (`scripts/test-e2e.sh`)
Simulates full lifecycle using Docker networks on a single machine:
1. Start 3 compose stacks on different Docker networks (simulate 3 ISPs)
2. Node A starts as leader — verify API responds, join token generated
3. Node B joins — verify it appears in Node A's node list
4. Node C joins — verify mesh has 3 nodes, WireGuard peering established
5. Add a VPN client — verify .ovpn downloads, contains 3 remotes
6. Kill Node A — verify Node B or C wins election within 10s
7. Restart Node A — verify it joins as follower
8. Kill all nodes except Node C — verify Node C enters ISOLATED mode
9. Restart Node B — verify Node C exits ISOLATED, election runs

**7.2 — iptables rules** (applied by router service on startup)
```bash
# Drop all traffic to/from VPN clients except allowed_lan
iptables -A FORWARD -i tun0 -d 192.168.100.0/24 -j ACCEPT
iptables -A FORWARD -i tun0 -j DROP
# Allow established/related
iptables -A FORWARD -m state --state ESTABLISHED,RELATED -j ACCEPT
```

**7.3 — TLS for the API and frontend**
In MVP: API runs plain HTTP on port 8080 (only exposed on LAN / mesh subnet in firewall).
Frontend runs on port 3000. Post-MVP: add Let's Encrypt via Caddy or certbot for the
frontend/API ports. Document this in `docs/tls.md`.

**7.4 — Secrets handling**
- `ADMIN_PASSWORD` env var → bcrypt hashed on first start, stored in `mesh_config` table
- `CF_API_TOKEN` env var → never stored in DB, read from env only
- WireGuard private keys → stored in `/data/wg/` with `chmod 600`
- PKI private keys → stored in `/data/pki/` with `chmod 600`
- Join token → stored in `mesh_config`, rotatable via UI

**7.5 — Logging**
All services log to stdout (Docker captures). Log levels: DEBUG/INFO/WARNING/ERROR.
Format: `[timestamp] [service] [level] message`. No log files in MVP.

## Router/firewall requirements (per node)

Each node's home router needs only two port forwards:

| Port | Protocol | Purpose |
|---|---|---|
| 443 | TCP | OpenVPN clients connecting |
| 51820 | UDP | WireGuard mesh between nodes |

No other ports need to be exposed. API (8080) and frontend (3000) are accessible via the
VPN tunnel or local LAN only.
